1. Instalação

Um container, um volume, uma variável de ambiente. Não há serviço adicional para subir — o estado local do DBee mora num bun:sqlite dentro do volume.

Pré-requisitos

  • Docker num host amd64. A imagem é compilada com bun build --target bun-linux-x64; numa VM arm64 o container não sobe.
  • Um volume persistente. Perder /data é perder todas as conexões cadastradas.
  • Acesso de rede do container até a porta direta do banco. Nunca o PgBouncer na 6432 — o DBee usa recursos de sessão que o pooler em modo transação não preserva.

Subir

# 1. O segredo que cifra as senhas das conexões.
openssl rand -hex 32

# 2. O container. Sem -p de propósito — ver "Rede e exposição".
docker run -d --name dbee \
  -e APP_SECRET="<o hex do passo 1>" \
  -v dbee-data:/data \
  ghcr.io/joaoviitorsx/dbee:latest

# 3. O token do primeiro acesso.
docker exec dbee cat /data/setup-token

Variáveis de ambiente

Variável Obrigatória Para quê
APP_SECRET em produção, sim Deriva a chave AES-256-GCM que cifra as senhas das conexões. O boot aborta se faltar com NODE_ENV=production.
DBEE_DATA_DIR não Onde ficam o SQLite e o salt de cifra. Padrão /data. Precisa de volume persistente.
PORT não Porta do servidor. Padrão 3001. Valor inválido aborta o boot.
DBEE_CA_CERT não CA em PEM para sslmode=verify-full contra um CA privado.
DBEE_COOKIE_SECURE não Marca o cookie de sessão como Secure. Só defina true quando o TLS termina no proxy.

Perder o APP_SECRET ou o volume /data = conexões perdidas. A chave de cifra vem do APP_SECRET e de um salt guardado dentro do SQLite. São dois pontos únicos de falha e não há recuperação — só recadastrar tudo. Guarde o segredo num gerenciador de segredos e declare o volume.

fonte: README.md “Subir em três passos” e “Variáveis de ambiente” · docs/operacao.md · CLAUDE.md regra 6 (PgBouncer).

2. Primeiro acesso

Abra o DBee pelo IP da tailnet ou pelo proxy interno. A primeira tela pede o token que você leu de /data/setup-token, e em seguida o usuário e a senha da sua conta.

O token é apagado do volume nesse instante. Nenhuma senha é gerada pelo sistema, nenhuma senha é impressa em log, e não existe uma variável ADMIN_PASSWORD — a primeira conta nasce pela tela, não pelo ambiente.

Se você perdeu o token antes de criar a conta, apague o arquivo de estado e recomece: o container recria /data/setup-token no próximo boot enquanto não houver nenhuma conta.

fonte: README.md · docs/operacao.md “Deploy no Dokploy”.

3. Primeira conexão

O formulário de conexão muda por motor. Ele não desabilita campos que não se aplicam: ele não os renderiza.

A diferença mais visível é o interruptor Permitir escrita. Ele existe no PostgreSQL e não existe no MySQL nem no MariaDB — e isso não é uma feature faltando, é a tela se recusando a mentir: nessas engines a garantia mora na credencial, então não há nada “por execução” que um interruptor pudesse ligar.

Teste antes de salvar

O botão Testar conecta de verdade e devolve dois tipos de aviso que valem mais que o “conectou com sucesso”:

  • Papel privilegiado. Se a credencial for superusuário (ou tiver privilégios amplos), o DBee avisa. Somente-leitura é proteção contra o acidente comum, não caixa de contenção contra um papel que pode tudo.
  • TLS com verify-full e host por IP. A combinação é recusada no MySQL/MariaDB: o driver zera o nome do servidor quando o host é um endereço IP, e a conferência de identidade cairia em localhost — ou seja, passaria sem verificar nada. Use o nome do host.

Nunca aponte para o PgBouncer. Sempre a porta 5432 direta. É regra do projeto, não preferência.

fonte: packages/shared/src/engine.puro.ts (CAPACIDADES) · docs/conexao-multi-engine.md · docs/multi-engine.md §3c · CLAUDE.md regra 6.

4. Papéis e permissões

Duas camadas independentes, e escrever exige as duas.

No DBee

  • admin — administra contas, cadastra e edita conexões, concede permissões, vê a auditoria inteira.
  • member — usa as conexões a que foi dado acesso. Não cria conexão, não administra conta.

A permissão de escrita é concedida por conexão, não globalmente. Uma pessoa pode escrever no banco de homologação e só ler no de produção, com a mesma conta.

Na conexão

Cada conexão PostgreSQL tem o próprio interruptor Permitir escrita. Com ele desligado, ninguém escreve por aquela conexão — nem um admin.

As duas camadas são conjuntivas. A escrita só acontece quando a conexão está habilitada e a pessoa tem a permissão. Foi assim que um achado de auditoria interna apareceu e foi fechado: um member sem permissão de escrita conseguia executar INSERT e DROP TABLE numa conexão MySQL, porque ali a garantia é a credencial e nada no caminho conferia a pessoa. Hoje há portão explícito, e um teste de integração que falha se ele sair.

fonte: migrations/004_user_roles.sql · services/portao-escrita.integration.test.ts · CHANGELOG.md (auditoria adversarial da fatia multi-engine).

5. O papel do lado do banco

A camada que o DBee não controla, e a que mais importa.

O DBee protege contra o acidente comum. Ele não substitui um papel restrito no seu banco — e em MySQL, MariaDB, libSQL, MongoDB e Redis o papel restrito é a garantia.

PostgreSQL — papel só de leitura

-- Tira do PUBLIC o CONNECT herdado: só quem receber GRANT explícito conecta.
REVOKE ALL ON DATABASE <db> FROM PUBLIC;
REVOKE ALL ON SCHEMA <schema> FROM PUBLIC;

-- Papel de login sem nenhum atributo privilegiado.
CREATE ROLE dbee_ro_<slug> LOGIN PASSWORD '<senha-forte>'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS;

GRANT CONNECT ON DATABASE <db> TO dbee_ro_<slug>;
GRANT USAGE   ON SCHEMA   <schema> TO dbee_ro_<slug>;
GRANT SELECT  ON ALL TABLES IN SCHEMA <schema> TO dbee_ro_<slug>;

-- Ler o que for criado DEPOIS. FOR ROLE é o dono que cria as tabelas —
-- sem ele, o default vale só para o que ESTE usuário criar.
ALTER DEFAULT PRIVILEGES FOR ROLE <dono> IN SCHEMA <schema>
  GRANT SELECT ON TABLES TO dbee_ro_<slug>;

MySQL / MariaDB — papel só de leitura

CREATE USER 'dbee_leitor'@'%' IDENTIFIED BY '<senha forte>';
GRANT SELECT ON nome_do_banco.* TO 'dbee_leitor'@'%';

Só isso. Sem GRANT ALL, sem WITH GRANT OPTION, sem PROCESS, sem FILE. Medido contra MySQL 8.4.11 e MariaDB 11.8.9: com esse papel, TRUNCATE volta 1142 e CREATE USER volta 1227 — os dois casos que escapavam de START TRANSACTION READ ONLY — e os dados ficam intactos depois da bateria inteira.

GRANT SELECT ON loja.* não é uma cerca em volta de loja. Medido: uma view com SQL SECURITY DEFINER criada dentro do banco concedido lê de bancos sem grant. O escopo do grant é a porta, não a parede.

fonte: docs/papeis-postgres.md · docs/papeis-mysql.md (medido contra MySQL 8.4.11 e MariaDB 11.8.9).

6. O que cada motor faz

Estado de hoje. Nada aqui é roadmap escrito no presente.

Motor Estado Faz Não faz Garantia
PostgreSQL completo árvore, catálogo, grade, SQL, escrita, DDL, exportação, ERD — transação
MySQL leitura árvore, catálogo, grade, SQL com cancelamento, ERD exportação, DDL, edição de linha credencial
MariaDB leitura idem MySQL idem MySQL credencial
libSQL leitura árvore, catálogo, grade, consulta credencial é o token JWT; selecionável no formulário claim "a":"ro" do JWT
SQLite planejado · bloqueado — tudo abertura do handle
MongoDB planejado — tudo papel read
Redis planejado — tudo ACL +@read

Por que o SQLite está bloqueado

Não é falta de tempo, é uma medição: bun:sqlite é síncrono, e uma consulta de 47 s produziu zero tiques num temporizador de 10 ms — o processo inteiro para, e não há timeout nem cancelamento. Num app multiusuário isso é negação de serviço por um SELECT malfeito. Sai do bloqueio com uma de duas decisões: rodar SQLite fora do processo principal, ou aceitar o risco explicitamente e documentá-lo.

Por que MySQL não tem escrita

Porque a garantia lá é a credencial, e uma credencial só tem um modo. Ou a conexão passa a guardar duas credenciais (uma de leitura e uma de escrita), ou a escrita fica desligada nessas engines. Prometer por lista de comandos proibidos é exatamente o que este projeto recusa — foi assim que o TRUNCATE escapou.

fonte: docs/multi-engine.md §1 e §2 · docs/multi-engine-progresso.md · packages/shared/src/engine.puro.ts.

7. Auditoria

Toda query executada vira uma linha em query_log, não só as de escrita. A linha guarda o SQL literal, a conexão e o banco, o status (ok, error, cancelled), a mensagem de erro quando houve, a contagem de linhas, a duração, se a execução foi somente-leitura de fato, quem executou e quando.

As consultas da grade registram os valores dos parâmetros num comentário -- args: [...], com aspas e quebras de linha escapadas — sem isso, “quem consultou o CPF de fulano” não era uma pergunta respondível, porque o log guardava $1.

Custo medido: a 1 milhão de linhas de log, o filtro por ator responde em 0,093 ms, e o INSERT de cada query custa 12,3 µs. Auditar tudo é barato o bastante para não ser opcional.

fonte: migrations/001_initial.sql (esquema) · migrations/006_audit_indexes.sql (os dois números, medidos) · CHANGELOG.md.

8. Rede e exposição

O DBee não é exposto à internet. Duas formas de acesso, nunca uma porta pública.

Pelo proxy interno (preferido)

Sem porta publicada. O proxy alcança o container pela rede interna e o domínio aponta para a porta 3001.

Porta bindada no IP da tailnet

Se publicar a porta, binde no IP 100.x do Tailscale — nunca em 0.0.0.0. E o bind sozinho não basta: o Docker escreve regras de NAT que furam o UFW. 

# A ordem importa: -I insere no topo, então o ACCEPT (inserido por
# último) fica ACIMA do DROP.
iptables -I DOCKER-USER -p tcp --dport 3001 -j DROP
iptables -I DOCKER-USER -i tailscale0 -p tcp --dport 3001 -j ACCEPT

O container roda como usuário não-root (uid 10001) e não monta o socket do Docker. A resposta carrega cabeçalhos de segurança com CSP restritiva — connect-src 'self' é a peça que transforma “o dado vazou do navegador” em “o navegador recusou o envio”.

fonte: docs/operacao.md “Segurança” · routes/cabecalhos.ts · CHANGELOG.md.

9. O que o DBee não faz

Uma seção de docs que lista limites vale mais que três de features, porque é a que evita a instalação frustrada.

  • Não provisiona banco. Ele opera um que já existe.
  • Não é SaaS e não tem plano pago. Roda na sua infraestrutura ou não roda.
  • Não instala agente no servidor de banco.
  • Não escreve em MySQL, MariaDB, libSQL, MongoDB nem Redis. Nenhuma delas tem transação somente-leitura que resista.
  • Não exporta fora do PostgreSQL.
  • Não contém um papel privilegiado. Num superusuário do Postgres, COPY … TO PROGRAM executa comando no host do banco de dentro de uma transação “somente leitura”. O DBee detecta e avisa; conter exigiria um parser de SQL, e parser de SQL sempre deixa um caso passar.
  • Não roda em arm64. A imagem é amd64.

fonte: README.md “Segurança” · CLAUDE.md regra 8 e §11.37 · docs/multi-engine.md §1 · docs/operacao.md.
